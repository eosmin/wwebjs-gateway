# Messages

The routes under `/v1/sessions/:sessionId/messages` (TDD §6.8 and §6.11). Sending goes through the [send queue](send-queue.md) and the [send policy](safety.md); the rest are reads and actions on one message, each one a call to the session's WhatsApp client, so the session must be `ready` (`409 SESSION_NOT_READY` otherwise).

## Sending

`POST /v1/sessions/:sessionId/messages` takes `to` and a `type`:

| `type`         | Fields                                                                                                                                                    |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `text`         | `body`                                                                                                                                                    |
| `media`        | `source` (`{ base64, mimetype, filename? }`, `{ url, filename? }` or `{ messageId }`), `caption`, `asDocument`, `asVoice`, `asGif`, `asSticker` (+ `stickerName`, `stickerAuthor`, `stickerCategories`), `asHd`, `viewOnce` |
| `location`     | `latitude`, `longitude`, `name`, `address`, `url`                                                                                                         |
| `contact`      | `contactId` or `vcard` (one of them). An id goes as a contact card; a vCard goes as text with `parseVCards`                                              |
| `contacts`     | `contactIds` (1 to 20)                                                                                                                                    |
| `poll`         | `name`, `options` (2 to 12), `allowMultipleAnswers`                                                                                                       |
| `event`        | `name`, `startTime`, `endTime`, `description`, `location`                                                                                            |
| `groupInvite`  | `inviteCode`: sent as `https://chat.whatsapp.com/<code>`, which WhatsApp shows as a card                                                                  |

The `mimetype` of a base64 `source` may carry parameters, as a voice note does (`audio/ogg; codecs=opus`). It must be a well formed media type (RFC 9110: no line break or control character, no stray `;`, at most 127 characters, otherwise `400 VALIDATION_ERROR`), and what the gateway keeps and sends to WhatsApp is only its bare type in lower case (`Image/PNG; charset=binary` becomes `image/png`). The one exception is `audio/ogg` whose `codecs` parameter is exactly `opus`, which is sent as the fixed text `audio/ogg; codecs=opus` that WhatsApp uses for a voice note; the sender's own text is never forwarded. The `Content-Type` that a download URL answers is read the same way. That a voice note sent this way arrives as a playable voice note is not verified with a live account yet (plan 10.4).

Every type also takes `quotedMessageId`, `ignoreQuoteErrors`, `mentions`, `groupMentions`, `linkPreview`, `parseVCards`, `sendSeen`, `waitUntilMsgSent` (these map one to one to `MessageSendOptions`) and `humanize` (`enabled`, `typing`, `recording`, `markSeenFirst`, `minReplyDelayMs`; `enabled: false` switches the typing off for this message even when the session humanizes its texts). A text without `humanize` gets the defaults of the session (`settings.humanize`, see [sessions.md](sessions.md)); other types get none.

- **`to`** is a phone number (spaces, dashes, dots, parentheses and a leading `+` are fine) or a WhatsApp id (`@c.us`, `@g.us`, `@lid`, `@newsletter`, `status@broadcast`). A number is looked up with `getNumberId`; an unregistered one answers `422 NUMBER_NOT_ON_WHATSAPP`. The answer, positive or negative, is cached in Redis for an hour and shared by all sessions (whether a number is on WhatsApp does not depend on who asks). The look-ups that miss the cache count against `LOOKUPS_PER_DAY`.
- **A channel id in `to`** (`@newsletter`) is a post to a channel: only `text` and `media` with a `caption` and `mentions` are accepted (anything else, a quote or a media flag included, is `400`, as is a reply to a channel post or a forward to a channel), there is no `humanize`, and the worker posts it with the channel call. `channels.post` is the same send with the channel in the path; see [channels](channels.md).
- **Answers.** By default the call waits up to `SEND_SYNC_TIMEOUT_MS` and answers `201 { jobId, status: "sent", message }`. If the send is still queued by then (or with `?wait=false`) it answers `202 { jobId, status: "queued" }`; the result arrives as the `message_sent` or `message_failed` event and at `GET …/send-jobs/:jobId`. A send that ended in failure answers the error itself (`WHATSAPP_ERROR`, `UNKNOWN_OUTCOME`, a policy code, …).
- **Order of the work.** The cheap checks come first: the body schema, the recipient (a look-up counts against `LOOKUPS_PER_DAY` on a cache miss) and the send policy; only then is media downloaded. A suppressed or blocked recipient never triggers a fetch.
- **Idempotency.** `Idempotency-Key` (1 to 128 characters, per session, kept 24 h). The same key with the same request answers the first result, or the job in flight, and adds `Idempotent-Replayed: true`; with another request it is `422 IDEMPOTENCY_KEY_REUSED`. A replay never waits: a key whose job is still queued answers `202` with the job at once, even with `wait=true`, and if the first request failed after the key was claimed but the gateway cannot tell whether the job was added (Redis did not confirm in time, `503 QUEUE_UNAVAILABLE` with `details.queued: "unknown"`), retries get `202` with a job id for up to 5 minutes, after which the key closes as `UNKNOWN_OUTCOME`; a retry never sends twice. A refusal that comes before anything was queued (`429 SEND_QUEUE_FULL`, or `503 QUEUE_UNAVAILABLE` with `details.queued: false`) gives the key back, so the same request can be repeated with it once the cause is gone, and a replay never counts against the queue limits. A key is looked up **before** any work, and the request is hashed as it was written (without `wait`), so a retry is answered with the stored result even if the recipient is now suppressed, the media URL now serves other bytes, the session defaults changed or the session is not ready. A key whose process died is closed as `UNKNOWN_OUTCOME` after 5 minutes; check the chat before sending again with a new key.
- **Policy.** The send policy is asked twice: right away (a cold send, a suppressed or unreachable recipient, … answer `422` at once) and again in the worker before dispatch (budgets and pacing, which delay and never fail).
- **Media.** `base64` is checked against `MAX_MEDIA_BYTES` after decoding. A `url` is downloaded by the gateway: only `http(s)` URLs whose host resolves to public addresses (the SSRF guard runs again on every download, the connection goes only to the addresses it returned, a redirect is an error), at most `MAX_MEDIA_BYTES`, within `MEDIA_FETCH_TIMEOUT_MS`. The type is the `Content-Type` of the server when it is well formed and does not contradict the bytes (text/html on a PNG is replaced by what the bytes are), or what the first bytes look like when it says nothing specific. `messageId` sends again the media of a message the session can still download. A media URL never uses `WEBHOOK_PRIVATE_HOST_ALLOWLIST` or `ALLOW_PRIVATE_WEBHOOK_TARGETS`: the URL comes from the caller and the file is sent on to a chat, so a host that webhooks may reach would be readable by every key that may send. A private host for media is declared apart in `MEDIA_PRIVATE_HOST_ALLOWLIST` (empty by default; each host listed there can be read by every key with `send`), and the metadata and link-local addresses stay closed for it too. Failures are `422 MEDIA_FETCH_FAILED` (a blocked URL is `400 VALIDATION_ERROR`).
- **Body size.** The send route and the reply route take bodies up to 40 MiB; every other route 1 MiB. A larger body is `413 PAYLOAD_TOO_LARGE`. A body that is declared larger than 1 MiB (or does not declare its size) is read only after the API key is checked: it needs a key that may send in that session, and it counts against the rate limit of the address like any request (so it counts twice). Without it the answer is `401`/`403`/`429` and the body is never read. A 32 MiB file is about 43 MiB as base64, above the 40 MiB of the route: a file between roughly 30 and 32 MiB sent as `base64` is refused by the body limit; send it as a `url` instead.
- **Memory.** A download, or the media of another message sent again by `messageId`, can hold its file about three times over while it is converted (the chunks, the joined buffer and the base64 text), so at most `MEDIA_FETCH_CONCURRENCY` (4) run at once; the others wait their turn, and the wait counts in the time of a synchronous send. The turns are shared between the sessions: when a permit is freed it goes to the session that has waited longest since its last turn, so a session with a long line of downloads cannot keep the others out (inside one session the order of arrival holds).
- **Queue limits.** A session may have `SEND_QUEUE_MAX_PER_SESSION` (500) sends waiting or running, and all the sessions together `SEND_QUEUE_MAX_TOTAL` (2000). The next one is refused with `429 SEND_QUEUE_FULL` (`details.scope` is `session` or `global`) and a `Retry-After` in seconds; nothing is queued. Redis keeps every job with its media, so the memory the limits allow is the limit times the size of the sends: size them for the host (see [send-queue.md](send-queue.md)).
- **Time limits.** The whole request, headers and body, must arrive within `HTTP_REQUEST_TIMEOUT_MS` (2 minutes) and the headers within `HTTP_HEADERS_TIMEOUT_MS` (30 s); a client that declares a `Content-Length` and stops sending is closed (checked every 30 s). A body of 40 MiB in 2 minutes needs 350 KB/s or more: raise the limit for slower uplinks. The answer is awaited at most 185 s (the longest call the adapter allows, 180 s, plus 5 s), then `504 WHATSAPP_TIMEOUT`.

`POST …/messages/:messageId/reply` takes the same body as a send, with `to` optional: without it the reply goes to the chat of the message, quoting it.

## Reading

| Route                                  | What it gives                                                                                  |
| -------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `GET …/send-jobs/:jobId`               | `queued`, `active`, `sent` (with the message) or `failed` (with the error)                    |
| `GET …/messages/:messageId`            | The message as WhatsApp Web has it                                                             |
| `GET …/messages/search`                | `query`, `chatId`, `limit`, `page`: messages WhatsApp Web has loaded                          |
| `GET …/stored-messages`                | The messages the gateway stored, newest first; page with `cursor`/`nextCursor` until it is null |
| `GET …/messages/:messageId/media`      | The file. The sender of a message chooses its type, so only formats a browser shows without running anything (JPEG, PNG, GIF, WebP, MP4, OGG, MP3, PDF) are served `inline`, under the bare type (`audio/ogg`, never `audio/ogg; codecs=opus`): upper case, spaces and the parameters of the sender (`; codecs=opus`, `; charset=utf-8`) are ignored when deciding and are not sent back. A type that is not well formed (a stray `;`, a line break or any control character) and every other type (HTML, SVG, `application/octet-stream`, anything unknown) is `application/octet-stream` as an `attachment`. Always `nosniff`, `sandbox` and `cache-control: private, no-store`. |
| `…/quoted`, `…/mentions`, `…/group-mentions`, `…/info`, `…/order`, `…/payment`, `…/reactions` | What the names say (`…/reactions` answers `[]` for a message nobody reacted to). A message that has no such part answers `404 NOT_FOUND` with a message that says which: `quoted` does not quote another message, `info` only exists for messages the account sent, `order` / `payment` are not an order / a payment |

## Actions

`react` (empty `reaction` removes it), `forward` (below), `star`, `unstar`, `pin` (`duration` 86400, 604800 or 2592000 seconds, any other value is a `400`), `unpin`, `PATCH` (edit the text of your own message), `DELETE` (`everyone`, `clearMedia`) and `DELETE …/status-messages/:messageId`. The pin call was repaired for WhatsApp Web 2.3000.1054445547 and is not verified with a live account yet (smoke test 5b in `sessions.md`). They answer `204` unless noted (`forward` answers like a send, `edit` with the message).

A **forward** is a send like any other: it goes through the queue, the policy, the pacing and the idempotency of the session, takes `?wait` and `Idempotency-Key`, and answers 201 or 202 like `messages.send`. WhatsApp does not say which message the forward created, and the gateway does not guess, so a finished forward is `{ jobId, status: "sent" }` with no `message` (the `message_sent` event has no `message` either). The forwarded copy reaches the event stream as its own `message_create`.

Scopes: `send` for sending, replying, reacting, forwarding and editing; `manage` for star, pin and delete; `read` for the rest.

## Polls, events and group invites

| Route | What it does |
| ----- | ------------ |
| `GET …/polls/:messageId/votes` and `GET …/messages/:messageId/poll-votes` | The votes of a poll message (`voter`, `selectedOptions`, `interactedAtTs`); `404` when the message does not exist, `400` when it is not a poll. Both routes give the same answer; votes also arrive as `vote_update` events |
| `POST …/messages/:messageId/vote` | `{ selectedOptions }` (option names) votes in a poll, replacing the previous vote; an empty list removes it; `404` for a missing message, `400` when it is not a poll or a name matches no option. `204` |
| `POST …/events/:messageId/response` | `{ response }`: `1` going, `2` not going, `3` maybe, `0` removes the answer. `204`; `404` for a missing message, `400` when it is not an event |
| `PATCH …/events/:messageId` | Edits an event you created. Send the whole event (`name`, `startTime`, and optionally `endTime`, `description`, `location`): a field left out is cleared. `isEventCanceled: true` cancels it. Answers with the message; `404`/`400` as a vote; `WHATSAPP_ERROR` for an event somebody else created or one already canceled |
| `POST …/messages/:messageId/accept-group-invite` | Joins the group of the V4 invite the message carries and answers `{ status }`; `404` when the message is missing or has no invite, `400` when the invite has expired |

Scopes: `read` for the votes, `send` to vote, answer or edit an event, `manage` to accept an invite. Polls and events are created with `messages.send` (`type: poll` or `event`).

## What a synchronous send does not publish

A send that was accepted with `wait=true` and ended while the caller waited does not publish `message_sent` or `message_failed`: the caller already has the outcome (TDD §6.8, [send-queue.md](send-queue.md)). The events are for sends whose caller did not get the answer: `wait=false`, a timeout that ended in 202, a replay, and a restart. A consumer that follows only the event stream will not see a synchronous send; it sees the message itself as `message_create`, which the pipeline publishes for every message the account sends.

## Not covered by a code check on purpose

There is no `extra` field. TDD §6.8 listed it among the options (the `extra` of `MessageSendOptions` is passed as it is to WhatsApp Web), but wwebjs spreads it into the message after everything the gateway validated (the chat, the text and caption, the media, the quoted message, the mentions), so a caller could change any of them after the send policy and the SSRF guard approved something else; a list of forbidden keys cannot be complete. The bodies of a send, a reply and an edit refuse it like any unknown field (`400 VALIDATION_ERROR`). It can come back as an allowlist of primitive keys if a real need appears. A look-up that the policy would only delay is refused with `POLICY_BLOCKED` instead, the one place where pacing is an error: the caller is waiting for the recipient, and a delayed look-up would hold the request for the length of the delay. A cache hit of a phone number skips the look-up budget, because it costs nothing; it tells a session whether a number is registered only when another session asked about it in the last minutes (a "no") or hour (a "yes").

## NUL characters (U+0000)

Postgres cannot store U+0000 in text or JSON, so the gateway never lets one through to it:

- **Incoming messages:** every NUL in the text, in a key or in the `raw` copy is removed when the message is mapped, before it is stored and before it is published. What is stored is what is published (`a\u0000b` arrives as `ab`); the message is neither lost nor split between the two.
- **API requests:** a NUL anywhere in the body, the query string or the path parameters is answered `400 VALIDATION_ERROR` with the message `The request contains a NUL (U+0000) character, which is not allowed`, for every route, instead of a `500` from the database.

## Coordinates and fields a real account lacks

`location` has `latitude` and `longitude` as **numbers** (degrees), in the send body, in the message and in the stored messages. Many descriptive fields of the response DTOs are optional because WhatsApp does not fill them for every account (a contact without `pushname`, a label without `hexColor`): see [ADR 0006](adr/0006-response-dtos-follow-what-wwebjs-delivers.md). If the message of a send does not fit its schema, the answer is still `sent` (the job id is there) but without `message`, and the error is logged: never a `500` for a message that went out.
