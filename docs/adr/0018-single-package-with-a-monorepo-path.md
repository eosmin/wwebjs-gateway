# ADR 0018: a single package now, with a path to a pnpm workspace

Status: Accepted (2026-10-27)

## Context

`omnichannel-platform`, whose toolchain this project mirrors (ADR 0002), is an Nx monorepo. This project is
one deployable service. A separate frontend that consumes the API may exist later, with a client generated
from the OpenAPI document. The question is whether to pay the cost of a workspace now.

## Decision

The repository is **one package**: `src/`, `tests/`, `scripts/` and `docs/` at the root, one `package.json`,
one lockfile, one Docker image. No Nx, no workspace layout, and no `apps/` or `packages/` folders.

The path, if a frontend project arrives and wants to live beside the gateway:

1. turn the root into a pnpm workspace (`pnpm-workspace.yaml` already exists for the settings pnpm 11 reads
   from it);
2. move the service into `apps/api`, keeping the scripts and the generators with it;
3. add `apps/web` for the interface and a package that holds the API client generated from
   `docs/openapi.json`, regenerated by the same `docs:gen` flow so it cannot drift;
4. keep the CI jobs of the root, each running per package.

Nothing in the code relies on the root layout beyond paths in the scripts and the configs, which is what
step 2 would change.

## Consequences

- One install, one set of checks and one image: a simple project to build and review.
- If the move happens, it is mostly path changes, because the OpenAPI document is already generated and
  verified as a build output.

## Alternatives considered

- **An Nx monorepo from the start:** pays for caching and project graphs when there is one project, and
  was already dropped from the mirrored toolchain.
- **A pnpm workspace with empty packages now:** structure with nothing in it, which is the kind of
  speculation to avoid until a second package exists.
- **A separate repository for the frontend:** also valid, and the same generated client serves it; this
  record only keeps the monorepo option open.
