# Implementation Plan — wwebjs-gateway

13 milestones (Phase 0 to Phase 12), 89 numbered steps. The specification is `docs/TDD.md`; this file is the checklist and the progress record. Work strictly in order; re-read the TDD sections cited in each step before implementing it.

Rules that apply to every step (details in `CLAUDE.md`): documentation ships in the same PR as the behavior; `pnpm validate:all` green before anything is proposed; the agent never runs `git commit`, `git push` or `gh pr create` without an explicit request from the owner; tick the step's box and update its row in "Progress tracking" as the last change of the step's PR.

- [x] **7.3** `webhook-dispatcher.service.ts`: subscribes to the event bus, and for each enabled webhook that wants the event (`WebhookService.forEvent`) stores a `webhook_deliveries` row (redacted copy: QR, pairing code and inline base64 out) and queues the `deliver` job with the full event shaped by the webhook's `includeRaw` and `mediaMode` (`webhook-payload.ts`). A failure of one webhook never stops another: a row that cannot be stored still gets its job (TDD §6.9) and is counted `unlogged`; a job that cannot be queued sends the row to `failed` (a dead letter that `retry` can send) and is counted `not_queued`. *Carried to 7.4:* the processor must deliver a job whose delivery row does not exist (the `unlogged` case: the job carries a `deliveryId` with no row, and `recordAttempt` answers null for it), and drop a job only when the webhook is gone. It must not drop it because the row is missing. *Carried to 7.6:* nothing yet fills `data.media` (`downloadUrl`, `base64`) on message events, so `mediaMode` only reduces what the event carries; the task that fills it, and the case of `includeRaw: true` while `INCLUDE_RAW` is off (the pipeline attaches no `raw`, so the webhook gets none; documented in `docs/webhooks.md`), are decided and closed there.
- [x] **7.4** `delivery.processor.ts` (BullMQ worker of `DELIVERY_QUEUE_NAME`, in `WebhooksModule` and in Bull Board through `mergeQueueSources`; concurrency `WEBHOOK_WORKER_CONCURRENCY`, lock longer than the request timeout). *Done when:* signature, retry and SSRF tests pass. Each attempt reads the webhook (`WebhookService.require`: URL, secret, `enabled`), runs `assertPublicHttpUrl` again and connects only to the addresses it returned (`postToPublicUrl`, `src/common/lib/public-post.ts`: Host and SNI from the URL, no redirect, `AbortSignal.timeout`), signs `${timestamp}.${rawBody}` over the exact bytes it sends, and writes the result with `recordAttempt`. Every non-2xx is a retry (TDD §6.9); the last attempt makes the delivery `failed`. The job now carries `webhookId` (the dispatcher and the retries pass it), so a job without a row is delivered and only a missing webhook drops it. A disabled webhook gets no event (its delivery goes to `failed` for `retry-failed`), except a `ping`. A manual retry of `qr`/`code` is refused (`400`). `ALLOW_PRIVATE_WEBHOOK_TARGETS` is refused at startup in production and keeps the metadata ranges blocked elsewhere. Jobs queued by 7.3 without a `webhookId` (none exist in any deployment: hosting is decided in 11.5) are not deliverable and end as an unrecoverable error. The job of a `qr` or `code` is kept five minutes after it finishes, not a day. The SIIT range `::ffff:0:0:0/96` and Alibaba's metadata address are now blocked. *Carried to 7.5/7.6:* see the follow-ups below; the integration suites that boot the whole application pause the `webhook-deliveries` queue unless they are about the processor.
- [x] **7.5** `retention.service.ts` (own `RetentionModule`; a BullMQ queue `retention` with two job schedulers, `purge` daily at 03:00 and `sweep-pending` every 10 minutes, registered with `upsertJobScheduler` so a restart replaces them). The purge deletes deliveries after `DELIVERY_RETENTION_DAYS`, messages through `MessageStoreService.purgeExpired` and, *carried over from 5.4*, calls `IdempotencyRepository.deleteOlderThan` with a 24 h cutoff; each runs even when another fails. The sweep sends a `pending` row older than 30 minutes whose job is not live in the queue to `failed` (`failUnqueued`) with a reason that tells a missing job from a job that finished or gave up without recording (`DeliveryQueueService.jobStates`, `DeliveriesRepository.listStalePending`), counts it as `gw_webhook_deliveries_total{result="swept"}`; it marks a row delivered only when the finished job returned `delivered` (fix PR `fix/7-webhook-delivery-bookkeeping`: the processor returns `'delivered'|'dropped'`, `DeliveryQueueService.jobStates` reads it, `DeliveriesRepository.succeedUnrecorded` moves pending to success, and the write of an attempt is tried 3 times on a transient database error). Documented in `docs/webhooks.md`. *Decisions:* the margin is 30 minutes and liveness comes from the queue, not from the age, so a row whose job waits for a long retry is never touched (the plan asked for a margin longer than the longest retry window, which depends on `WEBHOOK_MAX_ATTEMPTS` and has no upper bound; asking the queue is exact and needs no such window); the sweep marks `success` only when the job itself said `delivered`, and `failed` otherwise (marking `success` by age was rejected: a wrong `success` hides an undelivered event; re-queueing orphan rows from the sweep was rejected by the owner); a job that moves between states while the queue is read can be missed, which is harmless because its attempt records over the `failed` row. *Accepted limit:* once the job of a finished delivery has aged out of Redis (one hour, `removeOnComplete` 3600 s) a row left `pending` cannot be told from a lost job, so its reason says the receiver may have the event and a manual `retry` can repeat it (documented in `docs/webhooks.md`). *Cost:* `jobStates` still reads the jobs with their data (BullMQ has no read without it); reading the returned word adds nothing, and the cost stays tracked in 10.4.
- [x] **7.6** `tests/helpers/webhook-receiver.ts` (a reference receiver written from `docs/webhooks.md`: signature in constant time, timestamp tolerance, repeats, order by `seq`) and the integration suite `tests/integration/webhooks.integration.spec.ts`. *Done when:* every scenario listed in §7 Phase 7 passes (signature, retry then success, final failure, disabled webhook, event filter, QR redaction, the three media modes, `includeRaw`, the database down, the SSRF allowlist, `retry-failed`, `message_batch`, plus ordering by `seq` under retries). Also closes what 7.3 and 7.4 carried here. `mapMessage` fills `data.media` (`mimetype`, `filename`, `size` from the raw data, `downloadUrl` from `PUBLIC_BASE_URL`) on every message, for the sockets too; `WebhookMediaService` downloads the file once per event for the webhooks in `inline` mode and `shapeForWebhook` adds `base64` per webhook within `WEBHOOK_INLINE_MEDIA_MAX_BYTES`, only on `message` and the messages of a `message_batch`. *Decisions:* (1) `includeRaw: true` is refused with `400` while `INCLUDE_RAW` is off (rejected: leave it accepted and document it, which leaves a webhook that silently never gets what it asked for; rejected: make the pipeline attach `raw` when some webhook wants it, which stores personal data in the message table for every message because of one webhook); (2) a manual retry of an `inline` delivery sends the stored copy, with the `downloadUrl` and no `base64` (rejected: download again on retry, which needs a live session, may find the file gone and sends a different answer than the event had); (3) a file of unknown size is not downloaded to find out whether it fits (rejected: download and check, which loads an unbounded file into memory); (4) acks, edits and revocations never download; (5) at most 10 files are downloaded per event and only the webhooks in `inline` mode wait for the download (a large burst must not fill the memory or hold back the other webhooks). *Carried to 12.3:* check on a real account that the raw data of a media message names `mimetype`, `filename` and `size` and that `downloadUrl` and `inline` work (the fake client cannot show it).
