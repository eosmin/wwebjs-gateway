# Calls

The routes under `/v1/sessions/:sessionId/calls` (TDD §6.11). Each one is a call to the session's WhatsApp client, so the session must be `ready` (`409 SESSION_NOT_READY` otherwise). The library cannot place or answer a call: it offers a link for a scheduled call and rejecting an incoming one. The incoming calls themselves arrive as the `call` event ([events](events.md)).

| Operation          | Route                     | Scope    | Answer                    |
| ------------------ | ------------------------- | -------- | ------------------------- |
| `calls.createLink` | `POST …/calls/link`       | `manage` | `200` with `{ link }`     |
| `calls.reject`     | `POST …/calls/:callId/reject` | `manage` | `200 { confirmed: true }` or `202 { confirmed: false, note }` |

- **`calls.createLink`** takes `{ startTime, callType }`: `startTime` is an ISO 8601 date and `callType` is `voice` or `video`. The answer is `{ link }`, such as `https://call.whatsapp.com/video/XxXx`. When WhatsApp Web cannot make a link the library answers an empty string, and the gateway turns that into `502 WHATSAPP_ERROR` instead of passing it on. **Known limit (F14b):** on WhatsApp Web 2.3000.1054320313 the module that makes the link is not loaded and no bundle is known that loads it, so every call answers `502 WHATSAPP_ERROR`; the gateway log says `[lazy-module] WAWebGenerateEventCallLink is not available in WhatsApp Web <build> (no bundle is known to load it)`. The same module makes the call link of an event (`callType` other than `none` in `messages.send`).
- **`calls.reject`** rejects the call whose id the `call` event gave (`:callId`) through the VoIP stack of WhatsApp Web, the same function its own "Decline" button calls (F30; before that the library wrote a `call/reject` stanza by hand and never looked at the result, so the route said `204` while the caller kept ringing, H-LIVE-11). WhatsApp gives no answer to a reject, so the gateway answers only what the page can show:
  - `200 { "confirmed": true }`: the page listed the call before the reject, the stack took it, and within 3 s the page stopped listing it. That is the only signal the gateway trusts. **On WhatsApp Web 2.3000.1054491369 it is not seen**: the call collection of the page is empty while a call rings, so in practice every reject answers `202` there.
  - `202 { "confirmed": false, "note": "..." }`: the reject was handed to the VoIP stack of WhatsApp Web and its effect cannot be confirmed from the page. Do not assume the caller stopped ringing from this answer alone. In the live checks of 2026-11-14 (voice four times, video once) the phone of the caller stopped at once after every reject. The stack knows its own call, so the reject is asked even when the page does not list the call under the id of the `call` event. `lastEndedCall` of the page is **not** used as a signal: it was already the call while it still rang, and it was the call when the caller had hung up before the reject. At `LOG_LEVEL=debug` the log carries, for every reject, `rejectCall report from the page: {...}`: what the stack and the call collection look like (ids cut short, booleans, keys and types of `getCallInfo`, never a value).
  - `404 NOT_FOUND`: the gateway no longer holds the call (a ring buffer of `CALL_CACHE_SIZE` entries, default 50, [config](config-reference.md): the oldest goes when a new one arrives; the buffer is not kept across a restart, and each session has its own), never saw it, or already rejected it.
  - `502 WHATSAPP_ERROR` with `[call-reject]` in the cause: this WhatsApp Web build has no stack, or no function to reject with, or another call is the one the stack holds (it acts on the call it holds, not on an id, so the gateway refuses rather than hang up the wrong one).
  The answer used to be `204` without a body: a client that only checked for `2xx` keeps working, one that expected an empty body must read `confirmed`. **A reliable confirmation is still pending** (plan 10.4, F30b): candidates are `getCallInfo` of the stack before and after, and the end-of-call event of WhatsApp Web.

## The `call` event

`data` is a call: `{ id, from?, timestamp, isVideo, isGroup, fromMe, canHandleLocally?, webClientShouldHandle?, participants? }`. `from` is usually a `@lid` id, `timestamp` is the time the call arrived when WhatsApp gives none (it is 0 while the call rings), and `fromMe` is `false` when WhatsApp Web gives no `outgoing` flag, which is the case for every incoming call seen so far. Do not rely on `fromMe` to ignore the account's own calls: how a call placed from the linked account reaches the gateway is not verified (plan F12b). `canHandleLocally` and `webClientShouldHandle` are no longer given by WhatsApp Web and are left out. Exactly one `call` event is emitted per call id, however often WhatsApp Web touches the call again (it repeats the offer a few seconds later and again when the caller hangs up).  `participants` is not delivered for a group call yet (see TDD §2.5 and step 12.3).

## Calls and the message history

- **`call_log` is also a message.** A call that ends leaves a message of type `call_log` in the chat (who called, and the missed call), and it reaches the gateway as a `message` event like any other, besides the `call` event. A gateway that starts with an empty database (a new install, a restored backup, a database that was purged) is given the `call_log` messages that WhatsApp Web still holds for the chats it reads, so **old ones can arrive as new events**. A consumer must deduplicate by the id of the message and ignore the ones sent before the date its own integration began; the gateway does not know that date.
- **A call that rings while the gateway is off does not become a `call` event.** The `call` event is made when the page shows a call that is ringing; a call that has already ended when the gateway starts does not ring any more, so no `call` arrives. What does arrive is the missed call as a `call_log` message (seen in the live pass of 2026-11-13). Do not wait for a `call` to learn that someone called while the service was down: read the `call_log` messages.
- **Rejecting is not retroactive**: `calls.reject` only works on a call the gateway saw ring and still holds (see above).

## What the other wwebjs symbols map to

The fields of `Call` (`id`, `from`, `timestamp`, `isVideo`, `isGroup`, `fromMe`, `canHandleLocally`, `webClientShouldHandle`, `participants`) are the fields of the `call` event; `Call.reject` is `calls.reject`.
